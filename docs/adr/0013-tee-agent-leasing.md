# ADR 0013：租用遠端 TEE 執行 AI Agent（提案）

- 狀態：提案（2026-09-26），待決事項見最後一節
- 相關：ADR 0002（不加客製交易與預編譯）、ADR 0008（治理只靠硬分叉）、ADR 0009（儲存層與抽查）、ADR 0011（算力市場、bolt-vault）、ADR 0012（發行）

## 目標

委託者（以下稱「租用者」）付 BOLT，租用別人機器上的 TEE（可信執行環境），長時間執行一個 AI Agent：

- 執行者（機器主人）看不到 Agent 的程式狀態、記憶、金鑰與對話內容，也改不了它的行為。
- Agent 可以跨重啟、跨機器延續狀態（記憶、檔案、錢包）。
- 付款依實際運行時間結算，不需要信任執行者或租用者。

這和 ADR 0011 的「單次推論工作」不同：租約是長時間、有狀態、會對外行動（呼叫 API、簽交易）的服務。

## 結論摘要

| 項目 | 可行性 | 說明 |
| --- | --- | --- |
| 在鏈上驗證 Intel TDX quote | 可行 | Osaka 已有 P-256 驗證預編譯（EIP-7951，0x100，每次 6,900 gas）與 SHA-256（0x02），用一般 Solidity 合約就能驗證，**不違反 ADR 0002** |
| 在鏈上驗證 AMD SEV-SNP 報告 | 鏈上不可行，改由驗證小組 | 用 P-384 / SHA-384，沒有預編譯，純 Solidity 成本過高；沿用 ADR 0011 的驗證小組以 BLS 聚合簽章背書 |
| NVIDIA GPU 機密運算 | 有條件可行 | 不直接上鏈驗證；由已證明的 CPU TEE 內的程式在本機驗證 GPU 證明，並把 GPU 證據雜湊寫進 CPU quote |
| TEE 內持久儲存 | 可行，但要新設計 | 硬體封存（sealing）綁定單一晶片，TDX 甚至沒有封存金鑰；必須改用「與硬體無關的狀態金鑰 + 鏈上版本號」，見第 5 節 |
| 防止執行者竊看或竄改 | 對遠端與軟體攻擊者成立；**對有實體存取能力的執行者不成立** | 2025 年公開的記憶體匯流排攻擊（TEE.fail、Battering RAM、WireTap 等）可在實體存取下取出 TDX / SNP 的證明金鑰或解讀記憶體，Intel 與 AMD 都把實體攻擊列在威脅模型之外 |
| 保證可用性 | 不可行 | TEE 不保證機器會繼續開著；只能做到「不運行就不付錢」與「可以快速搬家」 |

整體判斷：**可行，但定位要清楚**。TEE 讓「執行者偷看或竄改」從「隨手可做」變成「需要實體攻擊硬體、且一旦被抓到會被罰沒」。設計上必須同時做到：

1. 在 Agent 可動用的價值上設上限（鏈上帳戶限額），不要把大額私鑰放進租來的 TEE。
2. 讓 TEE 被攻破時留下可證明的證據，並能罰沒執行者押金。
3. 狀態可以隨時搬到另一台機器。

## 1. 信任模型

**要防的對象**

- 執行者：可以看、改、重播、延遲所有進出 TEE 的資料；可以隨時關機、複製磁碟、重啟 Agent 並餵給它舊狀態；可以同時開兩份。
- 租用者：可能在服務完成後拒付。
- 網路上的其他人：可能冒充執行者或 Agent。

**信任的對象**

- CPU 廠商（Intel、AMD）的證明根金鑰、韌體與 TCB 公告。
- Agent Runtime 映像檔的原始碼：必須可重現建置，任何人都能算出相同的量測值。
- Boltchain 共識（驗證小組的 2/3 誠實假設，和 ADR 0009、0011 相同）。

**不保證的事**

- 可用性（執行者可以關機）。
- 流量後設資料的隱私：執行者看得到 Agent 連到哪些主機、傳輸量與時間點，TLS 只能保護內容。
- 對抗實體攻擊。只能靠押金、信譽，以及讓執行者選擇「放在雲端機房」的機器（見第 3 節）來降低風險。

## 2. 硬體選擇

| 技術 | 用途 | 證明鏈 | 鏈上驗證 |
| --- | --- | --- | --- |
| Intel TDX（第 4 代 Xeon 以後） | **主要支援**，整台機密 VM，記憶體不受 SGX EPC 限制 | TD quote（ECDSA P-256）← QE 報告 ← PCK 憑證 ← Intel SGX Root CA | 可以，Solidity + P256VERIFY |
| AMD SEV-SNP（EPYC 7003 以後） | 第二支援 | 報告（ECDSA P-384）← VCEK ← ASK ← ARK（AMD KDS） | 由驗證小組背書 |
| NVIDIA H100 / H200 / Blackwell 機密運算模式 | 本機 LLM 推論 | GPU 報告 ← 裝置憑證 ← NVIDIA 根憑證，另需線上撤銷檢查 | 不直接驗證，由 CPU TEE 內的程式驗證後綁進 CPU quote |
| Intel SGX | 不採用 | — | 記憶體小、移植成本高、側通道歷史多 |

**雲端機密 VM**：執行者可以在公有雲（例如提供 TDX / SNP 機密 VM 的雲）上跑，這時實體主機由雲端業者控制，執行者本人碰不到硬體，實體攻擊的風險大幅降低。但有些雲的機密 VM 透過 paravisor 只提供 vTPM 形式的證明，不一定拿得到原生 TD quote，要逐一確認。租約可以標記「雲端 / 自有機房」，由租用者自行選擇。

## 3. 元件

| 元件 | 內容 | 形式 |
| --- | --- | --- |
| `TdxVerifier` | 驗證 TD quote：簽章鏈、TCB 等級、QE 身分、撤銷清單；回傳量測值與 REPORT_DATA | 一般合約（不需要系統權限） |
| `TeeCollateral` | 保存 Intel 的 TCB Info、QE Identity、CRL、中繼憑證；**任何人都能提交**，合約用 Intel 根金鑰驗證簽章，只接受更新的版本（`tcbEvaluationDataNumber` 單調遞增） | 一般合約 |
| `ImageRegistry` | Agent Runtime 映像檔：映像 ID → 預期量測值（TDX 的 MRTD、RTMR0–2；SNP 的 MEASUREMENT）、原始碼 CID、建置說明 | 一般合約，任何人可登記，不審核 |
| `EnclaveLease` | 報價、託管、啟用（附 quote）、檢查點、按期結算、終止、搬家、押金與罰沒 | 系統合約（SNP 與 GPU 要用驗證小組，需要 epoch 掛勾），與 `ComputeMarket` 共用執行者登記與押金 |
| Agent Runtime（`bolt-art`） | 最小化 Linux 機密 VM 映像：可重現建置、唯讀根目錄（dm-verity）、產生 enclave 金鑰、取得 quote、解密狀態、執行 Agent、送檢查點；GPU 模式下驗證 GPU 證明 | 新 repo 或 `images/agent-runtime` |
| `boltchain enclave` | 執行者端：偵測 TDX / SNP / GPU、公布報價、啟動與停止 VM、轉送 quote 與檢查點、代送交易 | `crates/node` 子命令 |
| `boltchain lease` | 租用者端：選報價、託管、驗證 quote、交付金鑰、查看狀態、終止、搬家 | `crates/node` 子命令，另有 WASM 版 |
| 狀態儲存 | 加密檢查點：`bolt-vault` 格式，存在 IPFS，加上「保存委託」（見第 5 節） | `crates/vault` + 新的保存合約 |

## 4. 租約流程

### 4.1 報價與租用

1. 執行者登記機器：TEE 類型、CPU / 記憶體 / GPU、每小時價格、是否在雲端、網路頻寬。第一次登記時附上一份 quote，合約從 PCK 憑證取出平台 ID（PPID）並綁定到執行者，**同一台機器只能屬於一個執行者**，押金也因此無法重複使用。
2. 租用者選定報價，存入託管款（至少 N 個計費期），指定映像 ID、Agent 包的雜湊、檢查點間隔、最低 TCB 等級。

### 4.2 啟動與證明

1. 執行者用指定映像啟動機密 VM。
2. Runtime 在 TEE 內產生兩把金鑰：簽章金鑰 `S`（secp256k1，用於鏈上簽名）與加密金鑰 `E`（X25519，用於 HPKE）。私鑰從不離開 TEE。
3. Runtime 取得 quote，REPORT_DATA（64 位元組）填入：

   `keccak256(chainId, EnclaveLease 地址, leaseId, S 的地址, E 的公鑰, nonce)`，其中 nonce = 租用後合約指定區塊的 blockhash

   這樣一份 quote 只能用在這份租約、這兩把金鑰，而且不能拿舊 quote 重播。
4. 任何人把 quote 送到 `EnclaveLease.activate`：
   - TDX：合約呼叫 `TdxVerifier`，檢查簽章鏈、TCB 等級 ≥ 租約要求、量測值與映像登記相符、TD 屬性（debug 位元必須為 0）、REPORT_DATA 相符。
   - SNP / GPU：合約把 quote 排進待驗證清單，下一個 epoch 由驗證小組在鏈下驗證（Rust 實作，自行向 AMD KDS 抓 VCEK），以 BLS 聚合簽章回報結果。
5. 啟用後，`S` 成為這份租約唯一的「現役 enclave」。

### 4.3 交付秘密

- 狀態金鑰、API 金鑰等秘密一律用 HPKE 包給 `E`。`bolt-vault` 的 `add_recipient` 可以直接把既有的加密狀態加上新收件人，不必重新加密整份資料。
- 租用者端在包金鑰前**自己再驗證一次 quote**（本機驗證，不只相信鏈上結果），並確認 `E` 就是 REPORT_DATA 裡綁定的那把。

### 4.4 運行、檢查點與計費

- 每個檢查點間隔（例如 10 分鐘），Runtime 送出由 `S` 簽名的檢查點：`(leaseId, 版本號, 狀態清單 CID, 狀態根雜湊, 最近看到的 blockhash)`。
- 檢查點兼作「存活證明」：它證明 enclave 在那個區塊之後還在運行，並且狀態已經備份。執行者依有效檢查點的數量按期領款。
- 執行者沒有 BOLT 也能運作：檢查點與領款交易可由任何人代送，手續費從託管款扣（和 `ComputeMarket` 的中繼模式相同）。
- 上鏈成本：每個檢查點約一筆 5 萬 gas 的交易。可以改成每小時上鏈一次，中間的檢查點只在 P2P 上傳遞，由租用者自行保存。

### 4.5 終止與搬家

- 租用者可以隨時終止，只付到最後一個有效檢查點為止。
- 執行者可以宣告退出，必須給予通知期（例如 24 小時），期間照常計費。
- 搬家：在新機器上啟動、完成證明後，新 enclave 的 `S′` 取代 `S` 成為現役；舊 enclave 的簽章從此無效。新 enclave 從鏈上最新檢查點的 CID 取回狀態。
- 執行者失聯：連續 K 個檢查點缺席後，租用者可以單方面把租約轉到另一位執行者，不需要舊執行者配合。

## 5. TEE 儲存問題

### 5.1 為什麼不能直接用硬體封存

| 問題 | 說明 |
| --- | --- |
| 記憶體會消失 | 機密 VM 關機或重啟後，記憶體內容全部消失 |
| 封存金鑰綁定晶片 | SGX 的封存金鑰、SNP 的衍生金鑰都綁定單一顆 CPU；TDX 沒有提供封存金鑰。執行者退出或機器故障，資料就永遠無法解密 |
| 回滾攻擊 | 執行者把 Agent 重啟，餵給它一份舊的（但真實、簽名正確的）狀態，例如讓它重複支付、忘記已撤銷的權限 |
| 分叉攻擊 | 執行者用同一份狀態同時開兩份 Agent，讓兩份做出互相矛盾的行為 |
| 磁碟內容 | 執行者可以任意讀取、修改、替換 VM 的磁碟 |

### 5.2 三層設計

1. **工作磁碟（本機，隨租約消失）**
   - 每次啟動在 TEE 內產生隨機的磁碟金鑰，用 dm-crypt + dm-integrity 加密並驗證完整性；根目錄用 dm-verity 唯讀。
   - 執行者只看得到密文，改動會被偵測。重啟後磁碟金鑰消失，本機資料作廢，一律從檢查點恢復。
2. **狀態檢查點（持久，可搬家）**
   - Agent 的持久狀態（記憶、向量資料庫、檔案、設定）定期打包，用 `bolt-vault` 加密，上傳到 IPFS。
   - 內容金鑰包給兩類收件人：租用者的加密公鑰，以及現役 enclave 的 `E`。
   - 清單 CID 與版本號由檢查點上鏈（見 4.4）。
   - 遺失範圍 = 一個檢查點間隔；Agent 做重要動作（例如付款）之前可以先強制送一個檢查點。
3. **金鑰（不落地）**
   - 每個 Agent 有一把「狀態主金鑰」，只存在於 TEE 記憶體中，或以 HPKE 包好後存放。
   - 第一期由租用者保管並負責交付；第二期加入金鑰保管小組（見 5.4），讓 Agent 在租用者離線時也能自己搬家。

### 5.3 防回滾與防分叉

- **防回滾**：Runtime 啟動時從鏈上讀取最新的檢查點版本號與狀態根雜湊（讀取方式：透過多個 RPC 或輕節點驗證狀態證明，不能只相信執行者提供的 RPC），只接受吻合的狀態。
- **防分叉**：合約只承認現役 `S` 的檢查點；新 enclave 產生新的 `S′`，秘密只交給完成證明的那一份。
- **可證明的破壞**：如果同一把 `S` 對同一個版本號簽了兩份不同的狀態根，這只可能是 TEE 被攻破（正確的 Runtime 不會這樣做）。任何人都能把兩份簽名送上鏈，合約**罰沒執行者押金**，把這個平台 ID 列入黑名單，並把獎金給檢舉人。這讓實體攻擊從「無風險」變成「被抓到會損失押金」。

### 5.4 金鑰保管小組（第二期）

租用者不可能一直在線，Agent 需要能在執行者失聯時自動搬家。做法：

- 狀態主金鑰以 Shamir 秘密分享拆成 n 份，交給 n 個**在其他執行者機器上、已通過證明的保管 enclave**（t-of-n，例如 5-of-9）。
- 保管 enclave 只在「鏈上顯示新的 enclave 已成為這份租約的現役」時，才把自己那一份用 HPKE 包給新 enclave。
- 保管 enclave 分散在不同執行者、不同平台 ID 上，攻擊者要同時攻破 t 台機器才拿得到金鑰。
- 這是全新的機制，工作量大，放在第二期。

### 5.5 缺口：Boltchain 沒有「付費保存使用者資料」的機制

ADR 0009 的儲存層只保存**鏈的歷史**。ADR 0011 提到的「保存委託」尚未實作。Agent 的檢查點需要：

- 按期付費，由多個保存者各存一份（或 Reed-Solomon 分片，`bolt-vault` 已支援）。
- 用 ADR 0009 的抽查機制（驗證小組隨機挑戰、以 Merkle 證明回應）確認保存者真的還留著。抽查只看密文，不需要金鑰。
- 過期後回收。

建議把 `HistoryRegistry` 的抽查流程抽象化，新增 `BlobStore` 系統合約。在它完成之前，第一期可以只用執行者、租用者與 Agent 自己的節點釘住檢查點（風險：三方同時遺失時資料消失）。

## 6. Quote 驗證問題

### 6.1 TDX 的鏈上驗證步驟

1. 解析 quote（v4 / v5）：標頭、TD 報告本體、簽章資料。
2. 用 quote 內的證明金鑰（P-256）驗證「標頭 + 本體」的簽章：1 次 P256VERIFY。
3. 驗證 QE 報告由 PCK 金鑰簽名，且 QE 報告的 REPORT_DATA 等於 `SHA-256(證明金鑰 ‖ QE 驗證資料)`：1 次 P256VERIFY + SHA-256。
4. 驗證 PCK 憑證鏈到 Intel 根金鑰：葉憑證 + 中繼憑證各 1 次 P256VERIFY。中繼憑證驗證一次後快取；同一台機器的葉憑證也可以快取。
5. 從 PCK 憑證取出 FMSPC、CPUSVN、PCESVN、PPID，查 `TeeCollateral` 裡的 TCB Info 得到 TCB 等級，並確認 PCK 沒有被撤銷。
6. 查 QE Identity，確認 QE 的身分與版本。
7. 比對 TD 屬性（debug = 0）、MRTD、RTMR0–3 與 `ImageRegistry`，比對 REPORT_DATA。

估計成本：DER 與 quote 解析是主要開銷，快取命中時約數十萬 gas，冷啟動（要驗證中繼憑證）時可能到一兩百萬 gas，在 3,000 萬的區塊上限內。**需要實作後做基準測試**，也要把 `bench` 的最壞區塊測試納入（ADR 0002 的樹莓派考量）。

每份租約只在啟用與搬家時驗證一次，不是每個區塊，所以成本可以接受。

### 6.2 附帶資料（collateral）的新鮮度與撤銷

- Intel 會發布新的 TCB 公告（TCB Recovery），把舊的韌體版本降級為「過期」，並更新 CRL。
- 這些資料都由 Intel 的 TCB 簽章憑證簽名，**不需要信任提交的人**。`TeeCollateral` 允許任何人提交，驗證簽章後只接受 `tcbEvaluationDataNumber` 較新的版本，不能退回舊版。
- 風險：沒人提交新資料時，合約會繼續接受已經過期的平台。對策：
  - 節點內建一個工作，發現 Intel 發布新資料時自動提交（需要能連到 Intel PCS 的節點）。
  - 每份資料都有 `nextUpdate` 時間；過期太久時合約拒絕新的啟用，直到有人更新。
- 已經啟用的租約：新的 TCB 公告讓某平台降級後，任何人都能呼叫 `recheck(leaseId)` 重新評估，不符合租約要求的 TCB 等級時，租用者可以不受通知期限制立刻終止並搬家。

### 6.3 量測值政策

- TDX 的 MRTD 取決於 TDVF 韌體版本與 VM 設定（CPU 數、記憶體大小不影響 MRTD，但會影響部分 RTMR，需要實測確認）。每種執行者硬體組合可能產生不同的 RTMR0，`ImageRegistry` 要允許一個映像登記多組量測值。
- Agent 本身不放進映像：映像只含 Runtime，Agent 包的雜湊寫入 RTMR3（或 REPORT_DATA），租約指定允許的 Agent 包雜湊。
- 可重現建置是整個信任模型的基礎：任何人拿原始碼建置，必須得到相同的量測值，否則登記的量測值沒有意義。

### 6.4 SEV-SNP 與 GPU：驗證小組背書

- 驗證小組沿用 `ComputeMarket` 的機制，每個 epoch 從委員會抽選。
- 小組成員在鏈下用 Rust 驗證（SNP 需要向 AMD KDS 取得 VCEK 與 CRL；GPU 需要 NVIDIA 的撤銷檢查），以 BLS 聚合簽章回報結果；三分之二同意才算通過。
- 這個方式的信任假設比鏈上驗證弱（依賴小組誠實），因此租約要標示驗證方式，讓租用者選擇。
- 之後可以改成零知識證明（在 zkVM 裡驗證 SNP 報告，鏈上用 BN254 預編譯驗證 Groth16 證明），不需要改動其他部分。

### 6.5 平台身分與隱私

- PCK 憑證裡的 PPID 可以唯一識別一台機器。用途：一機一執行者、黑名單、信譽。
- 代價：機器的所有權關係在鏈上公開。執行者不願公開時，可以只提交 `keccak(PPID ‖ 執行者地址)`，但黑名單就只能針對執行者，不能針對機器。建議採用公開 PPID 的做法。

## 7. Agent 對外行動的安全

TEE 可能被攻破，所以 Agent 能動用的價值必須有上限：

- **Agent 的鏈上帳戶**：租用者的帳戶透過 EIP-7702（Osaka 已支援）委派給一份「限權錢包」合約，或另開一個合約錢包。現役 enclave 的 `S` 只是它的會話金鑰：
  - 每日支出上限、可互動合約的白名單、單筆上限。
  - 租用者可以隨時撤銷。
  - 換 enclave 時，舊的會話金鑰自動失效（合約讀 `EnclaveLease` 的現役 `S`）。
- **外部 API 金鑰**（例如 LLM 服務）：只以 HPKE 交給已證明的 enclave，並建議用有額度上限的金鑰。
- **對外連線**：所有 TLS 連線在 TEE 內終結；執行者可以阻擋或延遲連線，但無法看到內容。Runtime 應該記錄連線失敗，讓租用者判斷是否搬家。

## 8. 付款與押金

| 情況 | 處理 |
| --- | --- |
| 正常運行 | 依有效檢查點按期付款；和 `ComputeMarket` 一樣，收入先扣 20% 累積押金 |
| 執行者關機或斷網 | 沒有檢查點就沒有收入；連續缺席時租用者可以搬家。**不罰沒**，因為無法在鏈上證明是誰的錯 |
| 租用者拒付 | 託管款是預付的，執行者依檢查點直接領款，租用者無法拒付 |
| TEE 被攻破的證據（同版本雙簽） | 罰沒執行者全部押金，平台 ID 列入黑名單，檢舉人得獎金 |
| 平台被 Intel 撤銷 | 租約可以立即終止，不罰沒（非執行者可控） |
| 接單上限 | 依押金與信譽決定可同時承接的租約數量與託管金額上限，和 `ComputeMarket` 相同的公式 |

押金上限應該反映 Agent 的風險：租用者可以要求「押金 ≥ X」才願意租用。Agent 帳戶的支出上限應該小於執行者押金，這樣攻破 TEE 的預期收益低於損失。

## 10. 分期

1. **第一期：TDX、租用者保管金鑰（測試網）**
   - `TdxVerifier`、`TeeCollateral`、`ImageRegistry`、`EnclaveLease`（TDX 路徑）
   - `bolt-art` 最小映像：一個範例 Agent（例如呼叫外部 LLM API 的簡單 Agent）
   - 檢查點存 IPFS，由三方釘住
   - 限權錢包
   - 驗收：租用者在 A 機器啟動 Agent，Agent 寫入記憶；A 關機後在 B 機器恢復，記憶一致；用舊檢查點重啟會被拒絕；同版本雙簽可以被罰沒
2. **第二期：可自動搬家**
   - `BlobStore` 保存委託
   - 金鑰保管小組
   - SEV-SNP（驗證小組背書）
3. **第三期：GPU**
   - H100 / Blackwell 機密運算模式，本機推論
   - `ComputeMarket` 的 TEE 等級工作（ADR 0011 第 4 節第 3 層）改用同一套證明

## 11. 待決事項

1. **第一期是否只支援 TDX**：建議是。SNP 要等驗證小組裁決憑證完成。
2. **是否接受驗證小組背書的證明**（SNP、GPU），還是只接受鏈上可驗證的 TDX。
3. **平台 ID 是否公開**：建議公開 PPID，以便一機一執行者與黑名單。
4. **檢查點上鏈頻率**：每 10 分鐘（成本較高、遺失範圍小）或每小時。
5. **Agent 的 LLM 來源**：第一期是呼叫外部 API（簡單，但 API 業者看得到內容），還是直接等 GPU 機密運算。
6. **Runtime 映像由誰維護**：CAFECA 維護官方映像，還是開放任何人登記（`ImageRegistry` 本身不審核，差別在錢包與 CLI 預設信任哪些映像）。
7. **罰沒比例與押金門檻**：同版本雙簽是否罰沒 100%。
