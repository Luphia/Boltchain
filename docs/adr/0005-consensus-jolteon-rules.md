# ADR 0005：共識採用兩鏈 HotStuff 加 Jolteon 的投票與逾時規則

- 狀態：已採納（2026-09-25）

## 背景

開發方案寫的是「HotStuff-2」。實作時要決定兩件事：

1. **提交規則**：幾個連續 QC 才算最終。
2. **換 leader（view change）時怎麼保證安全又不卡住**。

HotStuff-2 論文的正常路徑很簡潔，但它的 view change 靠「等待 Δ 或收到 leader 的鎖證明」，
這要求對網路延遲上限 Δ 有正確估計。一旦估錯，就可能在逾時邊界出現活性問題。
Boltchain 的節點是樹莓派，放在家用網路上，延遲的變動範圍很大。

Jolteon（Gelashvili 等人，FC 2022；Aptos 2-chain DiemBFT 的基礎）用的也是兩鏈提交，
但 view change 改用明確的逾時證書（TC）。它的規則更少、更容易逐條檢查，而且已經在正式網路上運作多年。

## 決定

提交採兩鏈規則：區塊 B（第 r 輪）有 QC，且它的子區塊在第 r+1 輪也有 QC 時，B 即為最終。
共識層以純函式狀態機實作（`crates/consensus/src/engine.rs`），不做任何 I/O。

**投票規則**：對第 r 輪的提案，只有在以下兩種情況之一才投票，而且每輪最多投一票：

- 提案帶的 QC 就是第 r−1 輪的 QC；或
- 提案帶第 r−1 輪的 TC，而且 `qc.round ≥ tc.max_qc_round`。

**逾時**：

- 逾時訊息附上發送者的 high QC 和它的 `last_tc`，讓落後的節點看到 TC 就能跟上。
- 收到超過 1/3 權重的逾時，節點就跟著送出逾時（不必自己等到計時器到期）。
- 逾時時間指數退避，上限是基本值的 8 倍。

**最終性證明**：`CommitProof{qc, child_qc, child_header}`。
驗證者提交區塊後，把最終性證明放進公告一起送出。跟隨節點不參與共識，但只匯入帶有效證明的區塊。
`child_header` 是子區塊 header 的 RLP，它的 hash 就是 `child_qc` 簽署的區塊，
其中的 `parent_hash` 把子區塊綁到被提交的區塊上。

**資料可用性（DA）**：驗證者投票之前，必須：

1. 用 Bitswap 取得區塊的全部 chunk 並寫入 blockstore；
2. 在 parent 上重新執行，而且 header 完全相符。

因此 QC 同時證明了超過 2/3 的權重持有這個區塊的資料。

**安全狀態持久化**：`last_voted`、high QC 與已提交的區塊，在任何投票、逾時或提交送出前寫入磁碟。
重啟後用 `Engine::resume` 接續，不會在同一輪投兩次票。

## 驗證

決定性模擬器（`crates/sim`，`bolt-sim`）隨機產生以下條件：

- 4–10 個驗證者，其中最多 f 個拜占庭；
- GST 之前任意延遲與丟包，節點崩潰與重啟（故障總數有時超過 f，這類情境只檢查安全）；
- 拜占庭行為：沉默、雙重提案（兩個版本都送出）、對所有提案投票、無效區塊；
- 「Adversarial」：扣住提案，TC 之後從 genesis 分叉，連續幾輪的惡意 leader 互相串通。

每個情境都檢查：

- **安全**：所有誠實節點提交的鏈互為前綴；
- **活性**：故障不超過 f 時，GST 之後要持續有新的區塊提交（模擬時長 60 秒）。

| 測試 | 結果 |
| --- | --- |
| 情境 0–9,999（release，約 65 秒） | 0 安全違規、0 活性失敗 |
| 情境 10,000–19,999 | 0 安全違規、0 活性失敗 |
| 故意移除鎖定規則（`qc.round ≥ tc.max_qc_round`），3,000 個情境 | 抓到 65 次安全違規 |
| 故意允許同一輪投兩票，3,000 個情境 | **沒有抓到** |

CI 每次都跑 10,000 個情境。

「同輪兩票」的變異沒被抓到，原因是：要利用它，同一輪必須有兩個都能拿到 QC 的衝突提案，
這要求惡意 leader 精準地把誠實節點分成兩半。模擬器目前的對手還做不到這種針對性的分割。
這個規則由程式碼審查和單元測試保障；更強的對手留到 M4 補上。

**端對端**（`crates/node/tests/m3_consensus.rs`）：7 個驗證者在 localhost 上透過 libp2p 運作（BLS12-381 簽章、真實的 Bitswap 與 gossipsub）。
全部到達高度 5 之後關掉 2 個，其餘 5 個繼續把高度推進 5 以上，且各節點 head 一致。
另一個不參與共識的跟隨節點只匯入帶最終性證明的區塊，最後與驗證者一致。
重複執行 4 次都通過，每次約 30 秒。

## 後果

- 正常情況下，區塊在兩輪（約 2 個 slot）後就是最終的，不需要第三輪。
- 已知限制，之後處理：
  - leader 目前輪流擔任（round-robin）。M4 改成依質押權重做 VRF 抽樣，委員會由系統合約決定。
  - 投票目前走 gossipsub 廣播，而不是直送下一任 leader。7 個節點時沒有問題，委員會變大後（M4/M6）要改成直送。
  - `FetchBlock` 只能補回本地已經有 header 的區塊；其他的缺口靠「公告 + 最終性證明」的追趕路徑補齊。
  - 驗證者金鑰檔目前是明文 JSON（權限 0600）。M6 改用 EIP-2335 加密 keystore。
