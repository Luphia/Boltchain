# ADR 0014：SwarmStorage：付費保存使用者資料，抽查與歷史共用

- 狀態：已採納並實作（2026-09-26）
- 相關：ADR 0009（儲存層與抽查）、ADR 0011（bolt-vault）、ADR 0012（未質押存儲提供者）、ADR 0013（TEE Agent 的檢查點）

## 背景

ADR 0009 的儲存層只保存**鏈的歷史**：舊 epoch 由 16 位驗證者與 16 位未質押提供者保存，驗證小組每個 epoch 抽查，通過者平分存儲獎勵。

使用者自己的資料（ADR 0011 的輸入輸出檔、ADR 0013 的 Agent 檢查點）沒有人負責保存，只能靠當事人自己釘住。ADR 0011 提過「保存委託」，但沒有實作。

## 決定

新的系統合約 **`SwarmStorage`** 取代 `HistoryRegistry`，地址不變（`0xB017…0005`）：

- 鏈的歷史是其中一種保存對象，由發行量付費（每塊 1 BOLT，ADR 0012，規則不變）。
- 使用者的**保存委託**（deal）是另一種，由使用者付費。
- 兩者共用提供者名冊、抽查任務、驗證小組、認證與罰則。

名稱沿用 CAFECA 的 SwarmStorage 專案：`bolt-vault` 已經取代它的 `file_operator.ts`，鏈上合約接手它的保存與付費。

### 1. 提供者

- 沿用 ADR 0012 的名冊：質押的驗證者（id < 2^31）與未質押的存儲提供者（id ≥ 2^31）。
- 要承接使用者資料的提供者另外**開放報價**：`offerStorage(id, 容量 MiB, 最低單價)`，單價以「wei / GiB / epoch」計。可以隨時更改或關閉（`closeOffer`）；關閉只影響新的委託。
- **接單上限**：未質押提供者承接的未付款項總額不得超過 `5 BOLT + 10 × 押金`（和 `ComputeMarket` 相同）；驗證者以質押擔保，不設上限。未質押提供者可以用 `depositBond` 自行增加押金。

### 2. 保存委託

`createDeal(root, blocks, bytes, replicas, epochs, price)`，附上託管款：

- `root`：委託索引的 CID（dag-cbor `DealIndex`，見第 4 節），列出所有要保存的區塊。
- `blocks`：區塊數；`bytes`：總大小，計費時無條件進位到 MiB。
- `replicas`：副本數，1 到 16。
- `epochs`：保存期間，從目前 epoch 起算，最多 3,650 個 epoch（主網約 10 年）。
- `price`：願意付的單價（wei / GiB / epoch）。
- 每個副本每個 epoch 的費用 = `ceil(price × MiB / 1024)`；託管款 = 費用 × 副本數 × epoch 數，多付的部分結束時退回。

**指派**：合約以 `block.prevrandao` 為種子，從開放報價的提供者中隨機抽出 `replicas` 位，條件是：

- 報價開放、提供者仍在名冊中（驗證者狀態為 Active；未質押者為 active）
- 最低單價 ≤ 委託單價
- 剩餘容量 ≥ 委託大小
- 未超過接單上限
- 同一委託內不重複

最多嘗試 `64 × replicas` 次；找不到足夠的提供者時交易失敗，委託者可以提高單價或減少副本數。

**付款**：

- 每個副本（slot）記錄 `since`（開始的 epoch）與 `paidThrough`（已付到哪個 epoch，不含）。
- 任何人都能呼叫 `claim(dealId, slot)`：付款到目前 epoch 為止（只付完整的 epoch），而且到委託結束為止。
- 未質押提供者的收入先扣 20% 進押金（上限 64 BOLT），和歷史存儲獎勵相同；驗證者的收入直接給 owner。
- 委託結束後，任何人都能呼叫 `closeDeal`：替每個還在的副本付清款項，退回剩餘託管款，釋放提供者的容量。

**委託者可以**：

- `extendDeal(dealId, epochs)`：延長並補足託管款。
- `cancelDeal(dealId)`：把結束 epoch 改成下一個 epoch（目前這個 epoch 照付），其餘退回。

### 3. 抽查

- 每個 epoch 的抽查任務在歷史任務（16 個）之後，**再加 16 個委託任務**：從所有委託中隨機抽，再抽一個副本與一個區塊。
- 新副本有一個 epoch 的寬限期（`since` 當期不抽查），讓提供者從委託者或其他副本取得資料。
- 驗證小組、投票、認證、`recordAudit` 都和歷史相同。審計者的做法：
  1. 從任何節點取得委託索引（先問被抽查的提供者），找到抽中區塊的 CID。
  2. 只向提供者公布的 peer 要這個區塊；限時內拿到且雜湊正確才算通過。
- **通過**：不分發行量（使用者付的錢就是報酬）。歷史任務的通過才計入存儲獎勵。
- **失敗**：
  - 罰則與歷史相同：驗證者罰 1% 質押；未質押者燒 10% 押金並停用。
  - 這個副本立即解除：從上次付款到現在的款項**不付**，留在託管款中。
  - 合約嘗試抽一位新的提供者接手（從失敗當期開始計費）；找不到時副本空著，任何人之後都可以呼叫 `repair` 再試。
- `repair(dealId, slot)`：提供者已不在名冊中（驗證者退出或被罰出、未質押者停用或退出）時，任何人都能解除並替換該副本；解除時未付的款項同樣不付。

### 4. 委託索引（`DealIndex`）

dag-cbor，格式與 epoch 索引相同的分組方式：

- 根節點 `{v: 1, size, count, groups, root}`：`size` 為總位元組、`count` 為區塊數、`groups` 為分組 CID、`root` 為應用層的入口（例如 `bolt-vault` 的 envelope CID）。
- 每個分組是最多 1024 個區塊 CID 的清單。
- 提供者要保存根節點、所有分組與所有區塊。抽查也會要根節點與分組，所以提供者不能只存資料區塊。

鏈上只記錄根 CID、區塊數與大小，合約不驗證索引內容：

- 委託者填的區塊數比實際少：抽查範圍變小，吃虧的是委託者自己。
- 填的比實際多：抽中的位置超出索引時，審計者投「通過」，因為那是委託者的錯，不是提供者的。
- 索引本身取不到（根節點或分組）：提供者本來就該保存它們，算提供者失敗。

### 5. 節點

- **託管使用者的區塊**：節點加上 `--rpc-storage` 後開放兩個 JSON-RPC 方法（任何連得到 RPC 的人都能往節點塞資料，所以 RPC 要綁在 localhost）：
  - `bolt_hostBlocks(root, [[cid, data], …])`：逐一核對 CID 後存入本機，並把委託索引 `root` 記在 `<datadir>/hosted-deals.txt`。
  - `bolt_getBlocks([cid, …], dealId?)`：從本機讀取，缺的向網路要（先問該委託的保存者）。
- **資料來源公告**：節點每 20 秒在 storage topic 上公告自己能提供的委託索引與自己的位址（`DealAnnounce`）：
  - 替使用者託管的委託，公告 3 天。
  - 自己保存、而且有副本還在寬限期的委託（新副本或替補副本需要取資料）。
  - 公告只是提示，資料一律以 CID 驗證。
- **保存者**：每 2 秒巡檢自己（驗證者金鑰與 `--storage-account`）承接的副本，缺的區塊就先連上公告的來源，再向來源與其他副本要。
- **審計者**：依任務種類探測（`taskKinds`）。
- **CLI**（`boltchain storage`）：
  - `put --wallet <帳戶> <檔案> --replicas N --epochs E --price <BOLT/GiB/epoch>`：以 `bolt-vault` 加密（收件人是由帳戶私鑰衍生的加密金鑰）、建立索引、交給本機節點並送出委託。節點要保持上線，直到保存者取完資料（約一個 epoch）。
  - `get --wallet <帳戶> <dealId> --out <檔案>`：取回並解密。
  - `offer --wallet <帳戶> --id <提供者 id> --capacity <MiB> --price <BOLT/GiB/epoch>`（`--close` 關閉）、`deal <dealId>`、`settle`（領款或結束後結算）、`extend`、`cancel`、`withdraw`。
- **瀏覽器**：抽查任務顯示種類；委託任務的對象是委託編號、位置是委託內的區塊序號。

### 6. 升級方式

- 儲存佈局：`SwarmStorage` 保留 `HistoryRegistry` 全部狀態變數的順序，新狀態只加在後面；抽查任務的結構在最後多一個欄位 `kind`（0：歷史，1：委託），舊資料讀出來都是歷史任務。
- 新的 genesis（開發鏈、之後的主網）直接部署 `SwarmStorage`。
- 公開測試網以硬分叉 `swarm` 在某個 epoch 的第一塊替換程式碼（固定的 bytecode），分叉之前節點只做歷史抽查。

## 後果

- ADR 0013 的 Agent 檢查點、ADR 0011 的輸入輸出檔都有了付費保存的地方。
- 抽查負載增加一倍（每個 epoch 32 個任務）；每個任務只探測一個區塊，負擔仍小。
- 每個委託每個 epoch 被抽查的機率是 16 ÷ 委託數。委託很多時，單一副本很久才會被抽到一次；罰則（失去未付款項、押金與質押）要夠重才有嚇阻力。之後可以依委託金額加權抽查。
- 單價由市場決定，協定不設價；BOLT 價格變動時，提供者自行調整報價，已成立的委託維持原價。

## 已知限制與後續

- 指派用 `prevrandao`：出塊者可以小幅影響抽到誰。委託者與提供者串通只是自己付錢給自己，沒有發行量可套利，影響有限。
- 提供者拒收：目前被指派後不能拒絕；之後可以在寬限期內允許拒收並重新抽選。
- 多副本之間沒有「不同機器」的保證：同一個人可以用多個帳戶承接同一個委託的多個副本。之後可以結合 ADR 0013 的機器 ID。
- 修剪與巡檢目前是全量掃描，委託很多時要改成事件驅動（和 ADR 0009 的 M6 項目一起做）。
- 委託結束或副本解除後，保存者還不會刪除那些區塊（目前只有歷史修剪會刪資料）；要加上「沒有其他委託引用就刪除」。
- 公開測試網的分叉高度是第 2401 塊（epoch 4 的第一塊）；分叉前節點照舊只做歷史抽查。
