# ADR 0008：規則只能靠硬分叉修改；節點預留自動更新機制

- 狀態：已採納（2026-09-25）。§1、§2 已在 M4.5 實作（見文末），§3 在 M6
- 決定者：專案負責人
- 取代：ADR 0003 與 ADR 0006 §7 的治理設計（Safe 5-of-9、16 天與 2 天 timelock、UUPS 可升級合約、緊急暫停）
- 相關：ADR 0007（PoW 啟動，沒有特殊待遇的錢包）

## 決定

**鏈上沒有任何治理權限。** 不預部署多簽，也沒有 timelock、合約升級權、參數管理者或暫停開關。
協定規則（包括系統合約的程式碼與參數）只能透過**硬分叉**修改：發布新版節點軟體，在預定高度啟用新規則，由各節點營運者自行決定是否升級，和比特幣相同。

## 1. 系統合約改為不可升級

- 移除 SystemProxy 與 UUPS：系統合約的實作直接部署在固定位址（`0xB017…0001` 起）。
- 移除 genesis 裡的 Safe、兩個 TimelockController、CompatibilityFallbackHandler。
- 所有「管理」函式改成只接受 system 地址呼叫（`onlySystem`），也就是只有節點程式本身（在區塊執行時）能呼叫。一般交易永遠無法觸發。
- 移除暫停質押存入的緊急權限。
- **參數：**
  - `committeeSize`、`minBaseFee`、鎖倉相關參數改為協定常數，要改就硬分叉。
  - `gasLimit` 改由出塊者投票調整，和以太坊一樣：每個區塊最多比 parent 變動 1/1024，並受 15M–60M 的硬性上下限約束。這樣不需要任何管理者，也保留了隨硬體進步調整容量的彈性。
  - ParamRegistry 只保留唯讀的常數查詢，或者直接移除。

## 2. 硬分叉機制（節點端）

- **分叉表**：每條鏈（依 chain id）在程式碼中內建一份硬分叉清單：`Fork { name, activation, changes }`。
  - `activation`：PoW 與 PoS 階段都以區塊高度指定。
  - `changes`：新規則的程式碼路徑，以及可選的「不規則狀態變更」（在啟用區塊的系統呼叫之前，替換某個系統合約的程式碼或寫入 storage）。修正合約 bug 就是這樣做的。
- **分叉 ID**（類似 EIP-2124）：`fork_id = crc32(genesis hash ‖ 已啟用的分叉高度…) ‖ 下一個分叉高度`。
  - P2P 握手時交換分叉 ID，規則不相容的節點不互連，避免在分叉點後互相丟無效區塊。
  - 公告與 Bitswap 都在同一個協定命名空間下（`/bolt/<chain id>/…`），分叉 ID 納入協定版本字串。
- **啟用前的提醒**：節點讀到網路上出現更新版本的分叉 ID（有 peer 宣告了本機不知道的下一個分叉）時，在日誌與 RPC 中持續提醒營運者升級。
- **沒有「緊急」路徑。** 任何規則變更都要經過發布、營運者升級、到達啟用高度。發布時間與啟用高度之間的最短間隔是協定慣例（建議 ≥ 14 天），不是鏈上強制。

## 3. 自動更新機制（預留）

目的是讓營運者**自願**降低升級成本，而不是讓任何人能遠端改變節點行為。

### 發布清單（release manifest）

```text
{ version, chain_id, forks: [{name, activation}], min_notice_blocks,
  artifacts: [{target: "aarch64-unknown-linux-gnu", sha256, size, cid, urls}],
  source: {git_commit, reproducible: true},
  published_at }
+ 簽章：發布簽署者的 ed25519 簽章（m-of-n）
```

- 清單以 IPFS 發布（CID），透過 gossipsub `/bolt/<chain id>/release/1` 公告。二進位檔透過 Bitswap 取得，另附 HTTPS 鏡像。
- **可重現建置**：任何人都能從 `git_commit` 建出相同的 sha256 並自行驗證。CI 會附上建置證明。

### 節點設定：`--auto-update <off | notify | apply>`

| 模式 | 行為 |
| --- | --- |
| `off` | 不接收發布公告 |
| `notify`（**預設**） | 驗證清單並提醒營運者（日誌、RPC `bolt_pendingUpdate`），不下載也不安裝 |
| `apply` | 驗證後下載、比對 sha256、放到 `datadir/updates/`，在安全時機以新版本重啟 |

`apply` 模式的額外保護：

- **信任的簽署者由營運者在本機設定**（`--update-signers`，預設是軟體內建的一組，可以替換或清空）。需要 m-of-n 簽章才接受。
- **冷卻期**：清單發布滿 7 天才安裝，讓社群有時間審查原始碼與建置結果。
- **只接受有足夠預告的分叉**：清單中任何分叉的啟用高度都必須在「現在」之後至少 `min_notice_blocks`（對應 14 天）。否則只提醒、不自動套用。
- **可以鎖版本**：`--pin-version` 讓營運者停在特定版本，永不自動更新。
- **重啟方式**：節點寫好新版本後以特定結束碼退出，由 systemd / launchd 以新版本重啟。節點本身不修改系統檔案，也不需要 root。
- **回滾**：新版本啟動後若無法同步（例如 10 分鐘內沒有匯入任何區塊），自動回到上一版並停用 `apply`，等營運者處理。

### 發布簽署者的權力

- 發布簽署者在鏈上**沒有任何權限**，無法改變狀態、搬動資金或影響共識。
- 他們能影響的只有**主動選擇 `apply` 且信任他們**的節點。預設的 `notify` 不會執行任何東西。
- 營運者可以換成自己信任的簽署者，或只信任自己從原始碼建置的版本。

## 4. 取捨

- **好處**：
  - 鏈上沒有任何特權地址，符合 ADR 0007 的原則；
  - 規則變更必須取得節點營運者的實際支持；
  - 沒有「多簽被盜或被脅迫就能改規則」的風險。
- **代價**：
  - 系統合約出 bug 時只能硬分叉修補，至少要一次發布週期加上預告期，不能即時暫停。因此外部稽核（M7）與上線前的測試更重要；
  - 營運者沒有升級時，網路會分裂成兩條鏈，需要靠分叉 ID 與提醒降低風險；
  - 自動更新若被廣泛設成 `apply`，發布簽署者實際上會有影響力，所以預設是 `notify`，並加上冷卻期與預告期。

## 5. 實作排程

- M4.5（與 PoW 啟動一起，因為都要改 genesis 與系統合約）：
  - 移除 Safe、timelock、proxy 與暫停權限；
  - gasLimit 由出塊者投票；其他參數改為協定常數；
  - 硬分叉表與不規則狀態變更的框架（目前為空）、分叉 ID 納入 P2P 協定。
- M6（強化與測試網）：
  - 發布清單格式、簽章驗證、`--auto-update notify|apply`、冷卻期與預告期檢查、回滾；
  - 可重現建置與 CI 建置證明；
  - 在測試網實際演練一次硬分叉（包含不規則狀態變更）。

## 實作紀錄（M4.5，2026-09-25）

- 系統合約不再經過 proxy，直接部署在 `0xB017…0001`（質押）、`…0002`（共識）、`…0003`（獎勵）、`…0005`（歷史）。ParamRegistry 整個移除，`…0004` 留空。合約沒有任何升級或暫停入口，所有管理函式只接受 system 地址；對應的測試會確認這些地址沒有程式碼、呼叫會失敗。
- 參數：`committeeSize` 與最低 base fee 取自 genesis；gasLimit 由出塊者投票，每塊變動必須小於 parent 的 1/1024，並在 15M–60M 之內。節點以 `--gas-target` 設定自己要往哪個方向投。
- 硬分叉表在 `crates/primitives/src/forks.rs`，目前是空的。不規則狀態變更在啟用區塊的系統呼叫之前套用（替換程式碼、寫入 storage），會記在該區塊的狀態變更裡。
- 分叉 ID 依 EIP-2124 計算（CRC32 + 下一個分叉高度），放在 libp2p identify 的 agent 字串（`boltchain/<版本> fork/<id>`），而不是協定命名空間：這樣分叉啟用時不必換 gossip topic。規則不相容的 peer 會被斷線；peer 宣告了本機不知道的分叉時，節點會在日誌提醒升級。
