# ADR 0016：存證證書

- 狀態：已採納並實作（2026-09-28）
- 相關：ADR 0014（SwarmStorage）、ADR 0015（瀏覽器的存證驗證）

## 背景

ADR 0015 讓用戶上傳證明檔，在瀏覽器中比對鏈上證據，但證明檔要由應用方產出，一般用戶自己無法建立證據。這次讓任何人都能在瀏覽器上建立證據：

- 上傳一組檔案，付 BOLT 取得一張證書；
- 證書有一串容易輸入的代碼；
- 任何人都能以代碼或網址查到證書，並上傳檔案比對；
- 可以選擇公開原始檔案，供人下載。

介面要儘可能簡單，可操作的部分越少越好。

## 決定

### 1. 證書合約 `Certificates`

一般合約，不是系統合約：不需要硬分叉，也沒有擁有者、管理員或刪除功能。營運者部署一次（`boltchain wallet deploy-certificates`），瀏覽器節點以 `--certificates <地址>` 指定。

**檔案證據**
- 每個檔案以 keccak-256、sha-256 與大小表示。
- 葉子 `keccak256(abi.encode(bytes1(0x00), keccak256(abi.encode(k, s, size))))`，節點 `keccak256(abi.encode(bytes1(0x01), l, r))`，落單的節點往上帶。這就是 ADR 0015 的 `prefixed-abi-v1`，所以每個檔案都能匯出成一般的證明檔。
- root 由合約自己計算，不接受呼叫者提供。
- 一張證書最多 256 個檔案。

**不記錄檔名**
- 鏈上與保存委託中都只有雜湊與大小；檔名可能含有個人資料。
- 證書上的檔案以序號顯示；公開檔案下載時，副檔名依檔案開頭的位元組判斷。

**代碼**
- `bytes10(keccak256(abi.encode(root, 建立者, salt)))`，顯示成 16 個 Crockford base-32 字元，例如 `GC46-E3M4-SV4E-T7JT`。
- salt 由建立者選擇，所以代碼在付款前就已知道，付款後可以直接前往證書頁。
- 代碼不分大小寫；輸入時忽略連字號與空白，I、L 視為 1，O 視為 0。
- 同一代碼只能用一次。

**手續費全部付給儲存提供者**
- `issue` 把收到的 BOLT 全數用來建立 SwarmStorage 委託（ADR 0014），保存證書的 manifest（雜湊與大小的 JSON），公開時連同檔案本身。
- 委託的擁有者是合約，所以沒有人能取消它。任何人都可以用 `extend` 付款延長。
- 同一份委託索引只能對應一張證書（`codeOfDeal`）。
- 委託結束時退回的餘額留在合約中；證據本身永久留在鏈上。

### 2. 費用與保存期間

瀏覽器以 `/api/storage/quote` 報價，依開放中的報價：
- **副本**：3 份；提供者不足時減少，至少 1 份。
- **單價**：第 3 便宜的最低單價，保證抽得到提供者。
- **期間**：約一年；受 SwarmStorage 最多 3,650 個 epoch 的限制，每小時一個 epoch 的測試網約 152 天。

因此費用和保存的資料量成正比：
- 只保存證據：只有 manifest，以 1 MiB 計費；
- 公開檔案：加上檔案大小，費用較高。

### 3. 上傳與清理

**上傳**
- 公開檔案切成 256 KiB 的 raw 區塊，由瀏覽器計算 CID。
- 經 `POST /api/upload` 交給瀏覽器節點；節點核對 CID 後存入 blockstore。
- `POST /api/deal-index` 建立委託索引，並向儲存提供者公告（與 `boltchain storage put` 相同）。
- 請求本體最大 8 MiB，一張證書最大 256 MiB。

**清理**：上傳發生在付款之前，必須有上限並定期清理。
- 未付款的上傳合計不超過 2 GiB。
- 委託索引 6 小時內沒有對應的證書，就刪除它的區塊。
- 沒有任何索引引用的區塊，2 小時後刪除。
- 節點原本就有的區塊不列入清理。
- 清理紀錄存在 `<datadir>/cert-uploads.json`，重新啟動後繼續。

### 4. 付款：CAFECA

- 證書頁以 CAFECA 的簽章通道付款（`sendCalls`，gas 由平台贊助）。錢包網址由 `--cafeca-wallet` 設定，預設 `https://cafeca.io`。
- 第一次按下按鈕時登入 CAFECA 並開啟通道，同時上傳檔案、建立委託索引並計算代碼；按下第二次時付款。兩次點擊都會開啟 CAFECA 視窗，瀏覽器要求這必須在點擊事件中進行。
- 通道 30 天內有效，之後再建立證書時不必重新登入。
- 簽章通道需要 WebCrypto，所以建立證書必須在 HTTPS 下進行（`https://boltchain.cafeca.io`）。以 IP 位址開啟時，只能查詢與驗證。

### 5. 介面

`/verify` 只有兩個區塊：
- **查詢證書**：輸入代碼；頁首的搜尋框也認得代碼。
- **建立證書**：拖入檔案、一個「公開原始檔案」開關、一行費用說明、一個按鈕。

ADR 0015 的證明檔驗證移到頁尾的「進階」連結（`/verify?mode=proof`）。

`/cert/<代碼>` 是證書頁：
- **認證標章**：已驗證為藍綠色並有勾號，無法驗證為紅色並有叉號。
- **證書資料**：代碼、建立時間、區塊、建立者、檔案數、是否公開、保存期限、證據根雜湊。
- **驗證檔案**：拖入檔案，逐一顯示「符合第 N 個檔案」或「不在這張證書中」。全部檔案都比對過時，顯示「全部相符」。
- **下載**：公開時可以下載檔案。每個區塊都對 CID 核對，完成後再對證書的雜湊核對。
- 可以複製連結、列印；支援繁中／英文與手機寬度。

證書頁不相信節點：它取回 `Issued` 事件所在區塊的原始資料，核對 header 雜湊與 receipt trie，再用事件中的檔案雜湊重算 root。

## 驗證

- 合約：root 與 Rust 實作一致（1 到 9 個檔案）；委託由合約擁有、建立者無法取消、任何人可以延長；代碼重複、委託索引重複、付款不足、沒有檔案、超過 256 個、陣列長度不一致、提供者不足都會失敗。
- 瀏覽器節點：上傳、委託索引、報價、查詢；清理會刪除未付款的上傳，保留已付款的與原本就有的區塊。
- 跨語言：同一組 root、代碼與 CID 在 Rust、Solidity 與 verify.js 中一致。
- 端到端：本機開發鏈上有 3 位儲存提供者，CAFECA 以測試替身代替，由 Chromium 操作頁面，涵蓋以下情境：
  - 公開與只保存證據兩種證書；
  - 比對檔案；
  - 下載檔案並與原檔逐位元組核對；
  - 以小寫、無連字號的代碼搜尋；
  - 查不到的代碼、列印、英文、手機寬度。

## 已知限制

- 保存期間受 SwarmStorage 限制；到期後證據仍在鏈上，但公開檔案可能取不到，要延長只能呼叫 `extend`（介面尚未提供）。
- 真正的 CAFECA 付款需要使用者的 Passkey，只能人工測試。
- 建立者是 CAFECA 帳戶的地址，證書上不顯示代稱。
